# apps/server（Sidecar）

Sidecar 是运行 Hono 服务与 Agent 的 Node 进程：由 Electron main 以 `ELECTRON_RUN_AS_NODE=1` 启动，也能脱离桌面独立运行。本文说明当前实现的入口与契约；消息与 DTO 的精确定义在 `@coko/protocol`（`packages/protocol/src`）。工具调用经权限判定与审批，命令在模式对应的 Seatbelt 档位内运行，契约见 [权限判定与审批](../../docs/subsystems/permissions.md)；崩溃后被中断 Run 的启动恢复与结果确认见 [启动恢复与结果确认](../../docs/subsystems/recovery.md)。

## 使用或结构入口

```text
<electron> apps/server/src/index.ts --data-dir <dir> --log-dir <dir> [--ripgrep <rg>] [--app-version <version>] [--packaged]
```

| 输入 | 含义 |
| --- | --- |
| `--data-dir` | 必填，绝对路径；库文件为 `<dir>/coko.db` |
| `--log-dir` | 必填，绝对路径；日志为 `<dir>/sidecar.jsonl`（JSONL，10 MiB × 5 份轮转） |
| `--ripgrep` | 可选，绝对路径；给定时启动先运行 `<rg> --version`，失败按 `ripgrep-unavailable` fatal（不回退内置 grep），成功则以 ripgrep 版 grep 覆盖内置 grep（`src/adapters/ripgrep.ts`）。未给定时使用内置纯 JS grep。生效实现记入日志 `grep implementation selected { implementation, path?, version? }` |
| `--app-version` | 可选，版本号形态（如 `1.2.3`、`1.2.3-beta.1`）；写入 sidecar.jsonl 每条记录的 `appVersion` 统一字段。desktop main 传入 `app.getVersion()` |
| `--packaged` | 由打包产物启动（desktop main 在 `app.isPackaged` 时传入）。发布构建中此时不读下文标为"仅测试"的 `COKO_FAUX_SCRIPT`、`COKO_SANDBOX_EXEC`、`COKO_TEST_*`，并记 warn `test hooks ignored in a packaged build { variables }`（只记名字）；main 也不把它们交给 Sidecar。以构建期标志 `COKO_TEST_BUILD=1` 打包的测试构建（E2E 的 globalSetup）照常读取 |
| `COKO_FAUX_SCRIPT` | 仅测试：faux provider 脚本的绝对路径，格式见 `src/adapters/faux.ts`；开启后新建 Session 默认使用 `faux/faux-1`。脚本的 `requestLog` 给出时，每次模型请求前把上下文消息作为一行 JSON 追加到该文件 |
| `COKO_LOG_LEVEL` | `trace`…`fatal`，默认 `info` |
| `COKO_HOME` | 用户级资源目录（指令、Skills、命令），绝对路径，缺省 `~/.coko`（`src/config.ts`）。不是测试钩子：打包产物同样读取；与其他 `COKO_*` 一样不进入 bash 的命令环境。集成与 E2E harness 传入临时目录 |
| `COKO_SANDBOX_EXEC` | 仅测试：覆盖 sandbox-exec 的绝对路径（默认 `/usr/bin/sandbox-exec`），用于验证不可用时的 fail-closed |
| `COKO_TEST_TOOLS` | 仅测试：为 `1` 时注册测试宿主工具 `secret_probe`（`src/adapters/test-tools.ts`，声明 Secret `COKO_TEST_SECRET`） |
| `COKO_SECRET_<NAME>` | 仅独立运行模式读取的 Secret（ADR 0007），见下文。IPC 模式不读 |
| `COKO_TEST_HOLD_AFTER_TOOL` | 仅测试，需 `COKO_TEST_TOOLS=1`：该工具执行完后挂起、toolResult 不提交，直到 Run 被中止（`src/runtime/layers.ts`），用于在"已执行、未记录结果"处强杀 |
| `COKO_TEST_HOLD_BEFORE_CHECKPOINT` | 仅测试，与上一项同用：为 `1` 时挂起点移到 checkpoint 的 afterToolCall 之前（`file_change` 也不提交） |
| `COKO_CREDENTIAL_<PROVIDER_ID>` | 仅独立运行模式读取的 Credential，见下文。`<PROVIDER_ID>` 为 Provider ID 大写、非字母数字换成 `_`（`custom-provider-1` → `COKO_CREDENTIAL_CUSTOM_PROVIDER_1`）；不读取 `DEEPSEEK_API_KEY` 等按品牌命名的变量 |

未知参数、缺失、相对路径或不合形态的版本号都按 `invalid-arguments` fatal。源码目录按 [项目架构约定](../../docs/tech-stack/architecture.md#仓库架构) 划分：`http/`（Hono 路由、信任围栏与 cookie）、`ws/`（订阅与补发）、`application/`（协议到 agent / session 的映射）、`runtime/`（Effect 装配与关闭）、`adapters/`（Credential 与 Secrets、faux、ripgrep、Seatbelt、测试工具）、`control/`（控制通道）。

## 契约与生命周期

- **控制通道。** 有 Node IPC 父进程时经 IPC 收发 `SidecarToMainMessage` / `MainToSidecarMessage`；否则为独立运行，消息逐行写到 stdout，不接收 main 消息。启动依次发 `starting`、`ready { port, token }`；失败发 `fatal { code, message }` 并以 1 退出，`code` 取值：`invalid-arguments`、`ripgrep-unavailable`、`storage-<StoreError code>`（如 `storage-lease-held`）、`faux-script-invalid`、`recovery-failed`（启动恢复的查询失败）、`listen-failed`、`startup-failed`。不合 schema 的 main 消息被忽略并记录警告。
- **访问认证**（[ADR 0002](../../docs/adr/0002-local-service-access-auth.md)）。只监听 `127.0.0.1` 端口 0。所有请求先过信任围栏：`Host` 必须等于监听 authority，带 `Origin` 时必须是 `http://<authority>`，`sec-fetch-site: cross-site` 拒绝，失败 403。`POST /api/auth/exchange { token }` 只能成功一次，返回 204 与 `coko-session` cookie（`HttpOnly; SameSite=Strict; Path=/`，HMAC 绑定 authority，签名密钥只在进程内存）。`/api/auth` 下的路由只供 main 调用：按规范化后的路径（百分号解码、合并重复斜杠、去掉末尾斜杠、不区分大小写）判断，只接受原样路径、不带 cookie 的 POST，其余形态（含 `%65xchange` 等编码变体和经 renderer 代理、带 cookie 的请求）返回 404 且不消耗令牌；其余路由与 WebSocket 升级缺少有效 cookie 返回 401。令牌不接受作为 Authorization 头。
- **HTTP。** 路径常量为 `API_ROUTES` / `apiPaths`：workspaces（列表、登记已存在的绝对目录）、sessions（列表、创建、详情含条目；Session 带 `running` 与派生的 `activity`（idle / running / awaiting-approval / awaiting-confirmation / paused / interrupted；没有 Run 时按未回答的结果确认与上一 Run 的 run_end，启动扫描为全部 Session 建立）、`POST …/confirmations/:toolCallId` 回答结果不明的调用（`AnswerConfirmationRequest`，204；没有待回答的确认 404；见 [结果确认](../../docs/subsystems/recovery.md#结果确认)）、`POST …/approvals/:requestId` 回答待审批请求（`AnswerApprovalRequest`，204；请求不在等待中 409 `approval-not-pending`；scope 为 session / workspace / global 时先保存请求的建议规则，没有建议规则的请求只能 `once`，否则 400）、`PUT …/permission-mode`、`GET / POST / DELETE …/permission-rules`（返回 `SessionPermissionsResponse`）、`POST …/messages` 返回 202 与 `runId`（与 retry、continue 一样，有未回答的结果确认时 409 `confirmation-pending`）、`POST …/retry` 重新执行出错的上一轮并返回 202 与新 `runId`（不追加用户消息；上一轮没有以模型错误结束时 409 `nothing-to-retry`）、`POST …/abort`（停止；未送达的追加指令随 run_end 退回）、`POST …/steer { text }`（追加指令，204；当前工具批次结束后送达并提交为 user message；没有进行中的 Run 时 409 `no-active-run`）、`POST …/pause`（204；当前批次完成后停下，待审批请求 cancelled，Run 以 paused 结束；没有 Run 时 409 `no-active-run`）、`POST …/continue`（202 与新 `runId`，`run_start { trigger: continue }`；上一 Run 不是 paused / interrupted 时 409 `nothing-to-continue`，有未回答的 confirmation_request 时 409 `confirmation-pending`；路径见 `runPaths`）、`PUT …/model { model, thinkingLevel? }`（见下文 Session 模型）、`GET …/checkpoints`（`CheckpointListResponse`：有效上下文中的用户消息与回退代码到该处时涉及的路径）、`POST …/rewind { targetSeq, mode: conversation | code | both, dryRun? }`（200 `RewindResponse`：code / both 把目标锚点及之后追踪过的路径恢复为最早的备份、原先不存在的删除，返回 `restored` / `deleted` / `diverged`（当前内容与最后一次记录不一致，照常恢复）/ `untracked`（超限，不动）/ `outside`（其中位于 Workspace 之外或受保护的路径，照常处理，确认时单独警告）/ `skipped`（真实路径与记录不一致而不处理）；写入为临时文件 + rename；conversation / both 提交 `rewind { targetSeq }` 条目并丢弃运行时，下次 Run 的模型上下文跳过 [targetSeq, rewind) 区间；dryRun 不改文件、不提交条目）、`POST …/fork { targetSeq, title? }`（201 `{ sessionId, text }`：新 Session 同 Workspace 与模型，标题为界面按当前语言生成的 `title`，省略时沿用原标题，条目为 `fork_origin { sessionId, seq }` 与目标之前的有效消息、`permission_mode`、`permission_rule`（去掉 runId），原 Session 与文件不变）；rewind 与 fork 在 Run 进行中或等待审批时 409 `session-busy`、有未回答的结果确认时 409 `confirmation-pending`、启动恢复失败时 409 `recovery-failed`（messages、retry、continue 同样）、目标不是有效的用户消息时 400，路径见 `checkpointPaths`）、`GET / PUT /api/permissions`（默认模式与全局、Workspace 规则，带 revision；规则的工具名归一为规范名，未知工具 400 `details.reason = unknown-tool`；路径见 `permissionPaths`）、settings（`PUT /api/settings/:key` 带 `expectedRevision`，冲突 409；`permissions.*` 键只能经 /api/permissions 修改，此处 400）、providers（只有列表、`GET …/:id/references`（`ProviderReferencesResponse { sessions }`：引用它的 Session 数量，删除确认用；不存在 404）与删除，响应只含 `credential: { hint } | null`；删除时同一事务删除 Credential、清空引用它的 Session 的模型字段（档位回到 off）、默认模型设置指向它时改为 null，并清除明文缓存，用相同 ID 重新创建不会接回这些 Session；创建与更新只经控制消息 `provider.save`，见下文 Provider 与 Credential）、`GET /api/models`（已注册 Provider 的可用模型，测试时含 faux，各带会话可选的 `thinkingLevels`；以及新建 Session 的默认模型，没有时为 null）。错误体为 `{ error: { code, message, details? } }`。
- **分层配置。** `GET` / `PUT /api/config`：返回默认、全局与项目合并后的生效值、全局 revision 与项目文件诊断；`PUT` 以 revision 乐观并发整体替换全局值，过期返回 409 `revision-conflict`；通用设置接口拒绝 `config` 键。见 [配置](../../docs/subsystems/configuration.md)。
- **上下文用量。** `GET /api/sessions/:id/context` 与 `GET /api/workspaces/:id/context` 返回 `ContextUsageResponse`（窗口、阈值、预警、tokens、分项、已加载指令文件与诊断）；时间裁剪经 `application/context/usage.ts` 的 `transformMessages`（受 `context.trimOldToolResults` 控制）。faux 脚本可设 `contextWindow` / `maxTokens`。见 [上下文管理](../../docs/subsystems/context.md#上下文用量)。
- **压缩。** 运行时的 `compaction` 选项由 `sessions.ts` 接线（读该 Session 的条目与该 Run 的 `context.autoCompact`）；内置命令 `/compact [指示]` 展开为 `compact` 动作（`application/context/compaction.ts`），经动作输入的 `session.start` 开始 `run_start { trigger: compact }` 的 Run，没有可摘要的较早内容时 400 `bad-request`（`details.reason: nothing-to-compact`）。动作输入另有 `session.entries()`。用量接口的 `autoCompact.paused` 为 `SessionService.compactionPaused`（运行时内存的熔断状态）。见 [压缩](../../docs/subsystems/context.md#压缩)。
- **MCP 与 Secret。** `GET /api/mcp`、`PUT /api/mcp/servers`、`POST /api/mcp/approvals`、`POST /api/mcp/reconnect` 与 `GET / DELETE /api/secrets`；通用设置接口拒绝 `mcp.servers` 与 `mcp.approvals.*`。连接按 (Workspace, Server) 池化，Run 开始时连接，有序关闭时在存储之前关闭。IPC 模式下 main 发 `secret.store { name, ciphertext, hint }`，Sidecar 只存密文并回 `secret.store.result`；需要明文时发 `secret.decrypt`（10 秒超时）。Server 声明 resources 时注册资源工具，提示模板登记为 `/mcp__<server>__<prompt>` 命令。见 [MCP Server 连接、工具、资源与提示模板](../../docs/subsystems/mcp.md)。
- **Session 模型。** 新建时未指定模型，依次取设置 `defaultModel`、faux（测试）、第一个 Provider 的第一个模型；都不可用时为 null。Run 开始时 Session 的模型字段为空：没有任何可用模型时 409 `model-not-configured`；有可用模型时 409 `model-required`（Provider 被删除或升级时被清空，不自动选用默认模型，界面提示重新选择）。同一 Session 同时只有一个 Run（409 `run-in-progress`）。Thinking Level 与模型一起保存在 Session 上（`thinkingLevel`，新建为 off）：模型可选的档位为 off，推理开关打开时再加上目录中已配置的档位（`selectableThinkingLevels`，固定顺序）；创建与 `PUT …/model` 给出不可选的档位时 400，Run 进行中切换 409 `run-in-progress`；`PUT …/model` 不给档位时保留当前档位，新模型不能选它时回到 off。每个 Run 以 Session 的档位请求：off 按协议的默认关闭方式（OpenAI Responses 发送 `effort: "none"`，Chat Completions 不带 `reasoning_effort`，Anthropic Messages 为 `thinking: disabled`），其余档位发送配置的参数值；保存的档位在当前目录中已不可选时按 off。分叉的 Session 沿用原档位。
- **WebSocket**（`/api/ws`）。客户端 `subscribe { sessionId, afterSeq }`，`unsubscribe { sessionId }` 停止接收该 Session 的推送（renderer 当前不发送，打开过的会话保持订阅）；服务端先补发 `seq > afterSeq` 的 `entry`，再发 `subscribed { lastSeq, running }`，之后推送实时 `entry` 与 `progress`，不重复也不遗漏。`entry` 在 SQLite 提交后才发布；`progress` 不持久化。条目在线上为信封 `SessionEntryRecord`，客户端按 kind 判别的 `SessionEntry` 逐条校验并跳过不合格条目；各 kind 的 payload 由 agent 定义（`SESSION_ENTRY_PAYLOADS`），存储按注册表写入校验、读取迁移，读取时跳过的条目记 warn `session entry skipped { sessionId, seq, kind, payloadVersion, reason }`。每个 Run 的条目以 `run_start { trigger: submit | retry | continue | compact }`（第一次模型请求前提交）开始、以 `run_end { status, error?, undeliveredSteering? }` 结束（status 含 paused；`undeliveredSteering` 为 Run 结束时未送达的追加指令，按发送顺序），中间为 `message`（payload 是模型可见消息，role 为 user / assistant / toolResult），需要审批的调用在其 toolResult 之前有 `approval_request` 与 `approval_decision`；新 Session 的第一条是 `permission_mode`（初始模式，不属于任何 Run），之后的模式切换与 Session 规则增删为 `permission_mode` / `permission_rule`；回退对话提交 `rewind { targetSeq }`（不属于任何 Run），分叉出的 Session 第一条为 `fork_origin`。`progress` 依次为 `run_start`、`assistant_delta`、`tool_start` / `tool_update` / `tool_end`、`retry`，每个 Run 以 `run_end { status, error? }` 结束：它在 run_end 条目提交之后发出，条目提交失败（例如租约被夺走）时也发出，客户端据此结束运行中状态。模型错误文本在入库与推送（`retry.errorMessage`、`run_end.error.message`、`compaction_failed.message`）前经同一函数脱敏。
- **Provider 与 Credential**（[ADR 0004](../../docs/adr/0004-model-credentials-safe-storage.md)、[ADR 0010](../../docs/adr/0010-provider-one-shot-save.md)）。保存只有一条路径：main 发 `provider.save { mode: create | update, provider, credential?: { ciphertext(base64), hint } }`，Sidecar 在一个事务中写入配置与密文并回 `provider.save.result`（成功带 Provider，失败带 `{ code, message, details? }`，失败时两者都不写入）。`provider` 为 `ProviderFields`：`id` 由用户给出，须合 `PROVIDER_ID_PATTERN`（`^[a-z][a-z0-9-]{0,63}$`），新建时重复为 `already-exists`（`details: { field: 'id', id }`），更新不存在的 Provider 为 `not-found`；`api` 为三种协议之一；`baseUrl` 须为 http(s) URL；`models` 为 Model Catalog，每个模型带 `name`（空串表示用模型 ID）、`contextWindow`、`maxTokens`、`input`、`reasoning` 与 `thinkingLevels`，目录为空、模型 ID 重复、`maxTokens` 超过 `contextWindow` 或档位重复时 `bad-request`；没有 kind 与品牌预设。update 不带 `credential` 时保留原密文，带时替换并清除明文缓存。调用模型时发 `credential.decrypt { ciphertext }`，等待 `credential.decrypt.result`（10 秒超时），明文只缓存在内存，换密钥或删 Provider 时清除。获取可用模型：main 发 `provider.models { api, baseUrl, providerId?, secret? }`，Sidecar 按协议请求供应商的模型列表（OpenAI 两种协议为 `<地址>/models` 与 Bearer，Anthropic 为 `<地址>/v1/models` 与 `x-api-key`；不跟随重定向），回 `provider.models.result`（成功只有模型 ID，保持返回顺序并去重；失败带 `code`：`no-credential`、`bad-request`、`unreachable`、`upstream-error`（带 `status`）、`invalid-response`、`timeout`、`cancelled`）。`secret` 只用于这一次请求：请求期间登记为按值脱敏的值，不进入 CredentialStore 缓存、不落库；没有 `secret` 时用 `providerId` 已保存的 Credential。15 秒时限；`provider.models.cancel { requestId }` 中止进行中的请求。独立运行没有 main，不能保存 Provider。独立运行：只读 `COKO_CREDENTIAL_<ID>`（ID 大写、非字母数字换成 `_`），这些值启动时即登记为按值脱敏的来源；没有该变量的 Provider 没有 Credential（[ADR 0010](../../docs/adr/0010-provider-one-shot-save.md)）。
- **启动恢复。** 打开存储之后、开始监听之前扫描没有 `run_end` 的 Run，补提交过期的审批、补齐的工具结果、`confirmation_request` 与 `run_end { status: 'interrupted' }`，每个 Run 一个事务；单个 Session 恢复失败时该 Session 在恢复成功之前拒绝 Run、回退与分叉（409 `recovery-failed`），下次操作时重试；见 [启动恢复与结果确认](../../docs/subsystems/recovery.md)。
- **应用层结构。** `application/sessions.ts` 只有 DTO 与 Run 控制；`session-runtimes.ts`（运行时注册表、条目发布、上一 Run 状态）、`session-permissions.ts`（模式与规则的回放、锁、重新判定、审批回答）、`recovery.ts`（启动恢复、结果确认）、`checkpoints.ts`（Checkpoint 列表、回退、分叉与其间的排斥）。
- **上下文装配（M3）。** `application/context/` 每个领域（instructions、commands、skills、references、mcp、memory、usage、compaction）一个文件导出 `ContextContribution`，`context/index.ts` 按固定顺序组合（system section：指令 → Skills 索引 → Memory；输入展开：命令 → File Reference）；没有贡献时模型请求与 M2 相同。每个 Run 开始时 `SessionService` 取 system sections、工具（带权限类）、额外读取根与 hook 交给运行时；提交消息与 steer 先经 `expandInput`，结果为动作时调用 `actions[name]`（Run 进行中 409 `run-in-progress`，steer 中 400 `bad-request`）。有效配置由 `application/config.ts` 的 `ConfigService` 给出（默认 ← 全局设置键 `config` ← 项目 `.coko/settings.json`，见 [分层配置](../../docs/subsystems/configuration.md)）。各领域的路由在 `http/routes/<domain>.ts`，由 `http/routes/index.ts` 的 `DOMAIN_ROUTES` 挂载在 `/api` 下（config、commands、skills、files、mcp、secrets、memories、context）。登记明文的按值脱敏接在 `application/secret-redaction.ts`（工具结果进入运行时之前、每次模型请求、入库与推送），见 [按值脱敏](../../docs/subsystems/mcp.md#secret-的来源)。提交消息时 Run 进行中先 409 `run-in-progress`，不展开输入。
- **关闭。** `shutdown` 消息、IPC 断开、SIGTERM、SIGINT 触发同一次有序关闭（这些 Run 以 aborted 结束，不进入恢复）：停止 HTTP 并以 1001 关闭 WebSocket → 中断进行中的 Run 并等待其 `run_end`（status `aborted`）提交 → 按顺序关闭上下文各领域 → 关闭存储并释放租约 → 刷新日志 → 发 `shutdown-complete`，以 0 退出。`inspect-quit` 回答 `activeRuns`。

## 配置与限制

- 每个 Session 有一个 Permission Mode（read-only / default / accept-edits / full-access），模式与 Session 规则由条目回放，全局与 Workspace 规则由 `PermissionService`（`application/permissions.ts`）从设置读入并缓存；判定与规则语法见 [权限判定与审批](../../docs/subsystems/permissions.md)。
- 命令沙箱：启动时（打开存储之前）探测一次 sandbox-exec，日志记 `command sandbox selected { sandbox: 'seatbelt', executable }` 或 warn `command sandbox unavailable { executable, reason }`；不可用不阻止启动，受限档位的命令以 `sandbox-unavailable` 结束，full-access 不受影响。沙箱只约束文件写入，不限制网络与读取。
- Secrets（[ADR 0007](../../docs/adr/0007-secrets-from-registered-entries.md)）：只来自登记条目。`SecretService`（`application/secrets.ts`）在 IPC 模式解析库中的密文（经 `secret.decrypt` 取明文，只缓存在内存），独立运行只读 `COKO_SECRET_<NAME>`；不再按名字读取 Sidecar 自身环境中的同名变量。它同时是 `SessionService` 的 `secrets`（工具声明的 Secrets，只注入声明它们的那次调用）与 MCP 配置中 `${NAME}` 的来源；MCP 的错误与 stderr 尾部经已解密的值脱敏。
- `SessionService` 的 `extensions(ctx) => { hooks?, onEntry? }` 供 `runtime/layers.ts` 为每个 Session 运行时注册扩展（hooks 排在权限判定之后，onEntry 在每条条目提交并发布后调用）；当前注册 Checkpoint tracker，测试时另有 `COKO_TEST_HOLD_AFTER_TOOL` 的挂起 hook。回退代码读快照正文经 `SessionService` 的 `checkpoints`（`adapters/checkpoints.ts` 的 `openCheckpointStore`，与 tracker 共用 `<dataDir>/blobs`）。
- bash 的命令环境去掉 sidecar 自身的配置与凭据变量（`src/adapters/credentials.ts` 的 `HOST_ENV_EXCLUSIONS`）：`COKO_*`（含 `COKO_CREDENTIAL_*`、`COKO_FAUX_SCRIPT`、`COKO_LOG_LEVEL`），以及名字含 `API_KEY`、`TOKEN`、`SECRET`、`PASSWORD`、`CREDENTIAL(S)`、`AUTH` 的变量；`PATH`、`HOME` 等其余变量保留。工具输出本身不脱敏。
- faux 脚本的回复队列由所有 Session 共用，按模型调用顺序消费。
- 进程首次加载 `node:sqlite` 时向 stderr 输出一次 ExperimentalWarning。
- 集成测试从源码入口运行。本包不单独输出产物：桌面构建由 apps/desktop 的 `build/build.ts` 用 tsdown 打出 `dist/sidecar/index.mjs`（apps/desktop 以 workspace 依赖声明本包），其启动与对话由 apps/desktop 的 Electron E2E 验证，未打包路径与 `electron-forge package` 产物（`e2e/package-smoke.e2e.test.ts`）各有覆盖。
- ripgrep 版 grep 的参数：`--json --no-config --hidden --no-require-git --sort path --glob !.git`，目录搜索以搜索目录为 cwd、路径参数为 `.`。两种实现读取同样的忽略来源：各目录的 ignore 文件、`.git/info/exclude` 与全局 excludes（`core.excludesFile` 或 XDG 缺省文件），见 [忽略规则](../../docs/subsystems/context.md#忽略规则)。
