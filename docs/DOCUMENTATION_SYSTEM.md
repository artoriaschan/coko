# Coko 文档体系设计

文档围绕四个问题组织：要交付什么、为什么这样选择、当前系统如何工作、凭什么确认这些说法。规划、决策、现状和证据各有所属位置，通过引用关联，不复制为多份独立维护的正文。

本设计配合 [开发流程](DEVELOPMENT_WORKFLOW.md) 使用。下文的目标目录按需创建；模板与本地文档检查脚本 `pnpm run check:docs` 已提供，自动生成器和 CI 尚未实现。“落库”指写入项目文件并在具备 Git 后版本化，不表示新增数据库。

## 一 文档层级与事实归属

层级表示读者需要的上下文深度，不表示所有内容都服从最上层。根文档只说明整体与入口；具体事实由最近的责任模块维护。发现规格、实现或文档冲突时先标明差异并核对意图，不通过改写预期把缺陷解释成新行为。

| 层级 | 内容与目标位置 | 应包含 | 不应包含 |
| --- | --- | --- | --- |
| L0 指令与导航 | 根/子目录 `AGENTS.md`、`docs/README.md` | 触发条件、必要约束、到所属文档的链接 | 详细流程、所有模块的知识副本 |
| L1 产品意图 | `.scratch/<feature>/spec.md`、决策地图和票 | 用户问题、故事、验收、范围、依赖与确认依据 | 宣称尚未实现的能力已经可用 |
| L1 领域语言 | 根 `GLOSSARY.md`，确有多个领域时才建 glossary map | 已确认概念的一两句话定义、避免混用的词 | 数据库字段、实现设计、待决定的含义 |
| L2 项目技术规范 | `docs/TECH_STACK.md`、`docs/tech-stack/` | 已选技术、版本、项目级模块职责与技术约束；显式标注的候选项 | 功能需求访谈、任务状态、将选型当作已实现事实 |
| L2 功能设计 | `.scratch/<feature>/design.md` | 某次功能/变更的结构、接口、时序、失败保证、迁移和验证方案 | 搬入项目长期选型、擅自覆盖已确认约束、冒充当前架构 |
| L2 长期决策 | `docs/adr/NNNN-slug.md` | 决策、上下文、理由、真实备选方案、后果和验证要求 | 日常任务清单、逐轮问答、实现流水账 |
| L3 当前整体结构 | `docs/architecture.md` | 组合关系、进程和模块职责、主数据流、扩展入口 | 完整类型表、逐方法说明、重复 ADR 理由 |
| L4 当前子系统契约 | `docs/subsystems/<domain>.md` | 领域状态、接口语义、时序、错误、所有权与生命周期 | 全产品介绍、其他模块内部机制 |
| L4 当前包契约 | `apps/<app>/README.md`、`packages/<pkg>/README.md` | 使用入口、配置、能力、限制、扩展点 | 复制源代码/JSDoc或上层架构全文 |
| L4 可生成事实 | 源码 JSDoc、schema，未来 `docs/reference/` 生成区域 | 精确类型、命令、配置项、协议和工具目录 | 手写一份与源码独立变化的全量清单 |
| L5 操作指南 | `docs/user/`、`docs/cookbook/`、未来 `docs/development.md` | 前提、最短步骤、成功判断、常见失败与恢复 | 大段架构论证或未执行过的命令承诺 |
| L5 评审规范 | 未来 `CODING_STANDARDS.md`、`docs/defensive-patterns/` | 需要判断的代码规则；按错误类型或责任域组织 | 复制确定性工具已经执行的规则和阈值 |
| L6 变更与历史证据 | `docs/upgrade-guide/`、`docs/persistence-changes/`、`docs/postmortem/`、任务 evidence | 用户迁移、格式兼容性、事故原因、具体版本验证结果 | 被当作当前 API 或当前需求继续维护 |
| 会话交接 | 根目录 `hand offs/` | 用户要求保留的会话调研快照、源码入口、未决问题及继续工作步骤 | 替代正式规格、技术约定、ADR 或当前实现正文；将建议写成已批准决定 |
| 执行方法 | 项目 `.agents/skills/`，或已安装共享 skills | 可复用步骤、输入、完成条件、失败处理 | 产品事实、运行时契约、重复规则正文 |

`TECH_STACK.md` 是技术选型和精确版本的正文及读取入口，`docs/tech-stack/` 承接项目级详细技术约定。目录名与入口同名，表示同一份技术规范的分层展开；其中的 architecture 是规定的结构，`docs/architecture.md` 才是有实现证据支持的结构。UI 规则的正文在 `tech-stack/ui.md` 与 `tech-stack/ui-design-system.md`，测试规则在 `tech-stack/testing.md`，AGENTS 只保留读取触发条件和链接。

### 需求、已选型与实现的边界

先按职责和适用范围确定归属，再记录确认与实施状态。是否已实现、是否仍在讨论、文件篇幅都不能单独决定目录：已确认但未实现的项目技术约束仍在 docs；已批准的单次功能方案仍可留在其功能目录。

| 要回答的问题 | 唯一维护位置 | 与其他材料的关系 |
| --- | --- | --- |
| 用户需要什么，本轮交付什么 | 地图/决策票、功能 spec | 技术选型不自动扩大产品范围；规格引用既有约束 |
| 项目采用什么技术，必须遵守什么结构与边界 | TECH_STACK 与 tech-stack 专项页 | 作为功能设计输入；候选、可选和待决内容沿用原标注 |
| 本次变更如何实现需求 | 功能 design | 在已选型内设计；提出变更选型时显式标为提案 |
| 为什么接受这个重要取舍 | ADR | 保存确认依据和理由，规范保存生效约定，二者互相引用 |
| 当前代码实际上怎样工作 | 当前 architecture、subsystems、包 README | 由实现证据支持；偏离约定时记录差异，不能据此静默改写选型 |

改变用户已确认的选型、架构约束或产品承诺，需要对应用户确认；原授权范围内的常规工程细节可直接推进。候选方案只有获得确认依据后才能写成生效约定。研究和原型提供事实证据，不自动批准选择；任务方案获批也不等于其中所有建议都成为项目级规范。确有长期项目约束时，在确认后提炼进所属技术规范，功能设计引用其正文；不整份复制。

拆分、合并或重命名仅改变组织方式，保持原结论、确认状态、候选措辞和适用范围。正文迁到新路径不等于新决策获批，也不等于能力已交付。每次新增文档类别或职责目录，先在本节和目录图登记用途、边界及正文归属，再在同一批变更中创建内容、修正引用和导航；不可先另造目录再把现有规则当作不适用。

### 正式文档与任务材料的引用方向

`.scratch/` 是任务工作区及 local-markdown tracker。任务材料可以引用正式文档，也可以在任务工作区内相互引用；`.scratch/` 外的文件不得链接、嵌入、导入或要求读取其中的具体文件才能理解正文。把链接改成代码格式的具体路径仍是反向依赖，不能用这种方式绕过边界。

AGENTS、docs 导航、技术规范、ADR 和模块 README 必须独立成立。长期有效的决定、约束和必要证据先提炼到所属正式正文，记录确认主体/日期、适用范围、理由与必要的来源摘要；可链接正式文档、源码、测试、提交或可持久访问的外部来源。若唯一依据仍在任务文件中，先完整提炼必要信息，再让原任务指向正式正文，不保留一份独立维护的结论副本。缺少依据时标为未确认，不能因提炼而伪造批准或实施事实。

tracker 配置、模板和流程可以描述 `.scratch/<feature>/...` 等路径模式、检索方法与写入步骤。这些是操作协议，不是具体任务导航；当前任务由用户引用或按 tracker 规则现场查找，任务集合与进度不进入正式文档索引。

关闭任务或整理工作区前，核对长期材料已经独立保存、正式文档没有反向依赖。此规则不授权删除现有任务：`.scratch/` 中尚未完成的工作和唯一证据仍须保留。

## 二 类型、模板与目标目录

文档类型决定写作任务，目录决定它覆盖的范围。例如整体架构、子系统和包说明都可使用 `reference` 类型，但不能借此扩大为全仓库说明。

| 类型 | 何时使用 | 生成依据与格式 |
| --- | --- | --- |
| 需求规格 spec | 用户故事和验收已经确定 | 新版 `to-spec` 的模板；附来源与确认信息，不另维护一个 PRD 副本 |
| 技术规范 technical-spec | 维护项目已选技术及长期结构/接入约束 | TECH_STACK 和 tech-stack 专项页为格式示例；说明约束范围、确认来源、候选项及实现证据边界 |
| 设计提案 design | 某次功能或变更需要先设计 | [设计模板](templates/design.md)，引用规格、已选技术规范和研究/原型 |
| 决策 decision | 满足长期记录标准 | [ADR 模板](templates/decision.md)，只记录实际考虑过的方案 |
| 当前说明 reference | 架构、子系统或包行为需要解释 | [参考文档模板](templates/reference.md)，逐项对照当前代码、配置和测试 |
| 操作指南 guide | 用户或开发者需要完成明确任务 | [指南模板](templates/guide.md)，按实际执行顺序组织 |
| 验证 evidence | 一组检查支持某个版本的结论 | [证据模板](templates/evidence.md)，保留范围、环境、结果与限制 |
| 升级说明 upgrade-guide | 已交付能力发生外部可感知的不兼容变化 | [升级模板](templates/upgrade-guide.md)，以旧版本用户的操作为中心 |
| 事故复盘 postmortem | 缺陷隐蔽、系统性且值得避免再次排查 | [复盘模板](templates/postmortem.md)，说明机制和为什么原有检查没发现 |
| 索引 index / 流程 workflow | 导航或跨阶段工作方式 | 本目录 README / 开发流程为格式示例；只维护自己负责的入口和步骤 |

新维护文档使用 `kind` 和一句可检索的 `description`；规划与决策文档另记录状态。记录只有在消费者需要时才新增元数据；不维护无人使用的 tags、更新日期、全量包清单或手工哈希目录。旧文档随实际修改增补，不为补格式全仓重写。

以下是目标布局，不是现有目录清单：

## 三 从讨论中提炼决策

每轮讨论结束先归类，再写入文件。推荐方案在用户回答前只是提议；研究找到的事实不等同于用户选择。

| 材料 | 去向 | 提炼规则 |
| --- | --- | --- |
| 已确认的业务词义 | `GLOSSARY.md` | 一两句话定义，记录容易混淆的词，不带实现细节 |
| 用户需要的行为和边界 | 决策票 Answer，随后由规格引用 | 保留确认来源与适用场景，区分要求和建议；正式文档引用前先提炼必要结论 |
| 重要结构取舍及理由 | ADR | 已有同一决定就更新其事实；改变决定则新建后继记录 |
| 可逆的局部实现选择 | 设计提案、任务或代码 | 不为每个函数或样式调整建 ADR |
| 事实调查或原型发现 | 所属 research/原型结论 | 来源、日期或版本、证据、局限齐全 |
| 事故经过与漏检原因 | postmortem | 保留时间线和因果；后续架构选择另链接 ADR |
| 尚未决定或互相冲突的观点 | 未决问题或新决策票 | 保留阻塞关系，不进入当前行为文档 |

长期 ADR 沿用 Matt 的筛选标准：难以轻易撤销、未来读者缺上下文会困惑、确实存在取舍。需要记录的类别可为 `architecture`、`feature`、`testing`、`process`、`simplification` 或 `bug-fix`；类别不降低这三个标准，也不要求每类都建文档。

每条 ADR 至少说清上下文、决定和理由；有重要替代方案、后果与验证要求时写明它们。只记录实际考虑的选择；来源不够时注明缺口，不补造一段看似完整的讨论。

决策票保留当时问答与确认的历史证据；ADR 一旦成为长期理由的维护位置，票的 Answer 链接 ADR，后续不再独立改写一份相同理由。ADR 自身保存必要上下文和确认依据，不反向链接工作区中的票。规格记录行为要求，设计引用决定并描述本次方案，当前文档记录已实现契约。这四者并非同一正文的四份拷贝。

## 四 状态与晋升

状态属于文档自身，不借用任务状态。决策票 `resolved` 不表示实现完成，规格 approved 不表示产品已交付，ADR accepted 不表示已部署。

### 规格与设计

规格和设计以 `draft → approved → delivered` 表达本次工作进度；无法采用时标记 `withdrawn`，被新方案取代时标记 `superseded` 并链接后继。`approved` 需要记录用户确认或既有授权内工程决定的依据；仍影响关键行为的待决项必须明确，不能把“文档已写完”当成确认。

批准后变更范围时保留原始意图和变更原因，重新判断受影响场景、票和证据。新增尚未确认的关键内容退回 draft；局部实施进度记录在任务，不能把部分交付的整份规格标为 delivered。完成后规格作为该次交付的基线保留，新需求使用新规格或明确的新修订。

### ADR

长期决定统一保存于 Matt 约定的 `docs/adr/NNNN-slug.md`，保持路径稳定并使用两个互不替代的字段：

- `status`：`proposed`、`accepted`、`rejected`、`superseded`，表示决策是否成立。
- `implementation`：`not-started`、`partial`、`implemented`，表示接受的决定是否已经落地；只对 accepted/superseded 记录使用。

从 proposed 变 accepted 时写确认依据；从 accepted/not-started 变 implemented 时必须链接实际实现和验证证据。决定已接受但尚未实现时保持目标语气；已实现记录描述实际机制，并同步修正路径、名称等事实。撤销未实施决定可标 rejected 并说明原因；改变已实施决定新建 ADR，通过双向链接标记 superseded，不能把原决定改写成相反结论。

### 归档与删除

文档的 `lifecycle: active/deprecated/archived` 与上述批准和实施状态独立。字段、弃用条件、归档冻结、跳转兼容、删除条件及新会话读取规则统一由 [文档生命周期](DOCUMENT_LIFECYCLE.md) 维护。发生更新、移动、替代或归档时，同批修正活动引用、失效摘要和导航入口；只有正文完成不算维护完成。

## 五 文档生成与落库步骤

文档生成是基于证据的整理。Agent 可以起草内容，代码、测试、用户决定和运行结果分别支持不同类型的断言。

1. **识别输入。** 收集用户确认、规格场景、设计、实际 diff、测试和运行证据；没有 Git 时使用明确文件集合与修改前后内容，不能假造 diff 或提交版本。
2. **寻找已有位置。** 搜索相关术语、接口及页面引用，决定原地修订、增加章节或创建新文档。先修正已有正文，再更新任何派生索引。
3. **选择类型与范围。** 按前述矩阵确定读者、主题、文件路径和模板。上层文件只解释直接子项的职责；详细说明留给所属子系统或包。
4. **起草并提炼。** 保留事实、承诺、失败条件和后果；删除讨论流水、重复代码解释和与读者任务无关的过程。草案写目标，当前 reference 写已验证行为。
5. **验证声明。** 命令和操作教程按真实入口执行；接口语义对照源码及测试；来源只能支持其实际覆盖范围。缺运行条件的内容保留为设计/未验证说明，不升级成已验证操作指南。
6. **同步引用与入口。** 按 [生命周期流程](DOCUMENT_LIFECYCLE.md) 搜索路径、锚点及结论的消费者，同批修复活动引用、摘要、目录导航和任务入口；历史记录保留当时语义。
7. **检查与保存。** 核对 Markdown、链接、元数据、状态、模板占位符、生成内容和敏感数据。保存后读回；有 Git 时检查改动及暂存范围，提交推送按任务授权执行。
8. **给出回执。** 报告更新文件、支持证据、未验证项和实际保存/提交/推送状态。没有提交就只说本地保存，不把写文件称为已入远程库。

当前使用中文作为维护正文；产品 zh/en 字典与文档语言是不同约束。出现对外双语文档时，再按页面成对维护并核对含义。

## 六 实现变化如何触发维护

每次实现交付在所属任务中记录一张简短的文档影响表：变化 → 所属文档 → 动作 → 验证。没有文档影响可注明原因；不强制为小改动创建新文件。

| 变化 | 更新位置 | 必须核对 |
| --- | --- | --- |
| 用户流程、权限或可见行为 | 规格修订、所属 user 指南、UI 规则或参考页 | 语义是否获确认；用户步骤、失败反馈与实际行为一致 |
| 已选技术、版本或项目级架构约束 | TECH_STACK、所属 tech-stack 专项页；必要 ADR | 区分提案与已确认决定；同步受影响功能设计及已存在的实现说明，不能用代码偏差反向批准选型 |
| 进程/模块职责与调用关系 | architecture、所属 subsystem/包 README；必要 ADR | 责任、依赖与资源清理归属，当前与目标是否混写 |
| 接口、配置、默认值、错误 | 所属 JSDoc、包 README、subsystem；有生成器则重新生成 | 调用者与实现者、命令与配置优先级、文档示例 |
| Session/协议/存储格式 | 当前契约、版本化 persistence-change 记录；必要升级指南 | 旧读写行为、迁移、恢复、已发布格式样本不可改写 |
| 外部破坏性变更 | upgrade-guide，链接对应规格/决定和契约 | 谁受影响、旧新行为、迁移步骤、成功判断、回退限制 |
| 故障暴露流程缺口 | 必要 postmortem、测试或工具检查；必要规范 | 根因、漏检原因、负向验证是否真正拒绝原缺陷 |
| 设计被替代或机制移除 | 后继 ADR、当前文档、引用及相关任务 | 唯一理由和仍有效义务是否保留，是否还有消费者 |
| 生成的目录或网站 | 先修改 source/generator，再刷新产物 | 确定性、freshness、输出位置和发布状态 |

持久化变更记录属于历史证据：保存具体版本、旧新 schema 的来源、兼容性决定与测试引用。它不替代当前接口文档，也不替代面向用户的迁移步骤。没有真实变更时不创建空记录。

## 七 写作与检查层级

参考文档回答“是什么、规则是什么”，指南回答“怎样完成任务”；大段内容同时承担两种用途时拆分。长文开头给读者目的与导航，内容按使用、限制、设计深度展开；短文不强制套目录和空章节。段落一段一行，使用编辑器软换行。

图用来说明真实关系、数据流或状态；类型、配置和测试清单优先链接权威来源。重复字段可由未来生成器生成，正文解释含义；不手抄全量类型再建立另一套人工同步负担。代码示例要能编译或运行；仅展示设计的伪代码须明确标注。

| 检查层 | 内容 | 本次与后续接入 |
| --- | --- | --- |
| 结构 | 链接、锚点、frontmatter、占位符、ADR 编号重复、状态值 | `pnpm run check:docs` 本地检查，另含 `.scratch` 引用方向、active 文档可达性和 CLAUDE.md 链接；尚未接入 CI |
| 来源一致性 | 命令、API、默认值、模板与声明是否符合事实 | 人工/Agent 对照源码、决定和执行记录；可机械提取的部分再自动化 |
| 行为 | 示例、迁移、教程步骤和真实产物入口 | 按所属测试层运行；未执行时明确缺口 |
| 语义评审 | 范围、责任、决定依据、取舍、当前/目标混淆 | Standards 与 Spec 评审分别核对，绿色格式检查不能替代 |
| 生命周期 | 实施晋升、替代链、归档冻结、入口可达与生成 freshness | 弃用/归档的日期与“文档状态”说明、入口可达由 check:docs 检查；其余按生命周期流程从入口读回 |

内容过长时先把不属于本层的细节移至所属文档，再压缩重复语句，最后才考虑增加预算。不直接套用英文词数上限约束中文；后续按文件职责和实际阅读成本确定可执行预算。

## 八 现有材料与渐进迁移

当前维护流程、规范和模板，不生成尚未确定的产品事实。

- `TECH_STACK.md` 与 `tech-stack/` 共同维护项目技术规范；本次分层只迁移已有内容，不自动改写成当前 architecture，也不重新批准候选项。
- 已有地图和决策票保留路径与状态，通过 tracker 现场读取；首次确定术语才创建 GLOSSARY，首次满足标准的取舍才创建 ADR，并提炼完整的必要上下文。
- 新功能规格和实施票使用独立功能目录；不在决策票目录混入 ready-for-agent 实施票，不复制一份到 `docs/specs/`。
- `docs/agents/` 已记录本地 tracker、默认分拣角色和领域读取规则，并通过引用接入 ADR 状态、文档归属和生命周期要求。
- 首个可运行切片交付时建立对应当前架构、子系统和包说明，按真实内容创建索引；自动检查和生成器逐项接入，不先搭完整文档网站或知识库服务。
