## 按严重度

1. **lead 收到完成报告后只回复"OK"、未执行合入（工具经济 / 流程）。** M1 复盘第 5 条已采纳，M2 中仍在票 01、04、05、07、08、09、10、11 重复发生，其中一次 main 有 27 个失败用例。根因：完成报告以消息形式到达时，回复被当作对话应答而非执行步骤。改进（已采纳）：收到任何"票 NN 完成"消息时，第一个动作必须是运行合入脚本；在 M3 起的 implementer brief 中要求完成报告首行写 `MERGE-READY m3/<branch> <commit>`，作为 lead 的执行触发词。
2. **安全缺口在评审才发现（自动检查）。** F1（打包产物放行测试钩子）、F2（规则名大小写导致拒绝失效）、F5/J1（准备与执行之间的路径竞态）都通过了各票验收，在里程碑评审中才暴露。改进建议：为权限判定建立"拒绝规则必须生效"的属性测试（对每个工具名的大小写、别名形式断言 deny 生效）；为产物增加"发布构建不读取测试钩子"的 smoke（M6 的发布构建 E2E）。合入前轻量 Spec 评审（M1 复盘第 4 条）在 M2 实际没有执行，M3 起按票执行。
3. **Vite 预构建缓存使 main 与 worktree 结果不同（信息获取）。** 实施者在 worktree 全绿，main 首次运行 27 例失败。已采纳：深层导入的依赖加入 optimizeDeps.include；合入后在 main 复核保持为必做步骤。
4. **命令链不在失败处停止、--force 清理丢失修改（工具经济）。** 已采纳：lead 合入 / 清理脚本使用 `set -e` 或逐步检查退出码，不用 `worktree remove --force`。
