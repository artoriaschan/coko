# 增加自动审查模式：设计树与采纳记录

2026-11-20。用户调用 `/grill-me`，主题为“增加自动审查模式，AI 辅助判定”。三轮共 22 个问题：第一轮（Q1–Q8）用户全部同意；第二轮（Q9–Q19）除 Q9 外采纳推荐；第三轮（Q20–Q22）中 Q20 用户选了与推荐不同的读法并替代 Q9，其余采纳。用户在最后确认了完整清单。本文记录设计树与已采纳的决定；尚无规格、设计与实施票，未改代码，术语表与 ADR 也未改。

这件事此前在 [计划生命周期规格](../plan-lifecycle/spec.md) 中列为范围外（“帮我批准”改为由大模型审核），本次单独立项。

## 已核对的事实

来源：主会话阅读 [权限判定与审批](../../docs/subsystems/permissions.md)、[ADR 0005](../../docs/adr/0005-permission-mode-and-sandbox.md)、[ADR 0013](../../docs/adr/0013-external-hooks-tighten-only.md)、[ADR 0019](../../docs/adr/0019-headless-runs-deny-approvals.md)、术语表，以及 `apps/server/src/application/session-titles.ts` 与 `session-permissions.ts` 的片段。未运行测试，未做完整的依赖面调查。

- **判定是固定七步。** 拒绝规则 → 询问规则 → 受保护路径 → 越出可写根 → 模式放行 → 允许规则 → 询问。链路中没有任何模型审批者。
- **“帮我批准”就是 `accept-edits`。** 它只自动放行可写根内的 write / edit；bash、MCP 工具、定时任务等仍然询问。菜单现有三项：请求批准（`default`）、帮我批准（`accept-edits`）、完全访问权限（`full-access`）；read-only 不在菜单中，但在 Shift+Tab 循环内。
- **已有非用户回答审批的先例。** PermissionRequest Hook 可以代答第 7 步的询问，提交 `approval_request` 与 `approval_decision { by: hook }`；Hook 的 allow 越不过前四步、提权与计划审阅。
- **已有辅助模型请求的先例。** 会话标题用会话当前模型发一次无工具请求（`toolChoice: 'none'`、15 秒超时、输入经 Secret 按值脱敏），记为 `model_request { purpose: 'title' }`。`purpose` 现有取值为 turn、compaction、summary、title。
- **无界面运行。** 需要审批的调用在 PermissionRequest Hook 之后立即拒绝（`by: headless`）；ADR 0019 反对的是“没有人时默认批准”，并指明需要免审批时由调用者显式给出更宽的模式或允许规则。
- **ADR 0013 拒绝 prompt 型 Hook 的理由**是无人值守时额外花费模型费用且不受 Goal 预算约束。压缩摘要请求的 usage 已计入 Goal 预算，说明 Run 内的辅助请求可以纳入预算。
- **模式宽窄。** 子代理取根 Session 当前模式与其定义上限中较窄者（`narrowerMode`）；批准计划时所带的模式不得宽于进入规划前的模式。
- **定时任务与 Goal Round。** 在 GUI 下用 Session 当前模式运行，询问照常等待用户。`schedule_create`、`schedule_update` 属于 automation 类，只有 full-access 放行。
- **计划生命周期阶段一**（票 07）会把 `plan` 从 `PermissionMode` 中移除并给 `permission_mode` 条目升版。

## 已采纳的决定

### A 形态与边界

- **A1（Q1）新增模式取值。** 新增 Permission Mode 取值 `auto-review`，与 `accept-edits` 并存。不改写 `accept-edits` 的语义，避免已保存该模式的历史会话变成由模型放行命令；不做成与模式正交的开关，沿用 ADR 0005 的单一模式。
- **A2（Q2）审查者的管辖范围。** 审查者只回答第 7 步的询问，与允许规则、Hook 的 allow 同位。拒绝规则、询问规则、受保护路径、越出可写根、沙箱提权、计划审阅都不经它。判定顺序不变。
- **A3（Q3）模式放行与沙箱。** 与 `accept-edits` 相同：Workspace 内读取、可写根内的 write / edit 不送审；命令沙箱档位为 workspace-write，审查放行的命令照样在 Seatbelt 内运行。
- **A4（Q10）宽窄排序。** read-only < default < accept-edits < auto-review < full-access。子代理取窄与计划批准卡的上限都按此顺序，不加特例；`permissions.defaultMode` 可以设为 `auto-review`。

### B 审查者

- **B1（Q4）结果。** 只有两种：放行，或转交用户（出普通审批卡并附审查者的理由）。审查者不能直接拒绝调用。
- **B2（Q5、Q15）失败语义。** 超时、报错、输出无法解析、没有可用模型、预算耗尽，一律转交用户，不放行。
- **B3（Q6、Q17）模型与超时。** 用会话当前模型，与标题请求同一取法；首版不新增“审查模型”设置。超时 15 秒。
- **B4（Q7、Q12）可见上下文。** 用户消息、本 Run 已发生的工具调用（名字与参数）、待审的这一次调用；MCP 工具另带工具描述。不给工具结果，不给助手的正文与思考。
- **B5（Q13）什么算用户授权。** 有效上下文中用户亲自提交的消息、当前 Goal 的目标与成功条件、已批准的 Plan。压缩摘要、子代理的派发 prompt、由模型写的定时任务 prompt 不算授权，只作为“助手委派的任务”标注给审查者。审查子代理的调用时，用户意图取根 Session 的。
- **B6（Q12）送审范围。** 到达第 7 步的调用都送审，包括 bash、MCP 工具、Workspace 外的读取、带 worktree 隔离的子代理派发。automation 类（`schedule_create`、`schedule_update`）不送审，始终转交用户。
- **B7（Q18）审查策略。** 首版用内置的固定审查提示，不提供用户自定义策略；用户用拒绝、询问、允许规则收紧或放宽，这些都先于审查者生效。内置必须转交的类别：删除或覆盖 Workspace 外的数据、不可逆的 git 操作与推送、发布或部署、把 Workspace 内容或凭据发往外部、读取凭据类文件、下载后直接执行、安装全局软件或改系统配置、明显超出用户授权范围的动作。拿不准一律转交。
- **B8（Q17）时序。** 审查只在调用第一次到达第 7 步时运行一次。同一批的多个调用按现有顺序逐个审查，不并发，不缓存审查结果。审查途中用户切换模式的，审查结果作废并按新模式重新判定；切换到 `auto-review` 时已在等待的审批卡不补送审，留给用户。

### C 与现有机制

- **C1（Q14）回答顺序与无界面运行。** 第 7 步的回答顺序为 PermissionRequest Hook → 审查者 → 用户。无界面运行允许使用 `auto-review`：审查者放行的照常执行，审查者转交的按现有规则立即拒绝（`by: headless`）。GUI 下的 Goal Round 与定时任务不变，转交后照常等待用户。
- **C2（Q15）费用与预算。** 审查请求记为 `model_request { purpose: 'review' }` 并带 runId，计入消息用量和 Goal 的 Token 与费用预算。发请求前做预算检查，预算已耗尽时不发审查请求，直接转交用户。
- **C3（Q16、Q21）条目与理由。** 审查者放行时提交 `approval_request` 与 `approval_decision { outcome: allowed, scope: once, by: 'reviewer', reason }`。审查理由只给用户看，不进主模型的上下文；用户拒绝后主模型看到的仍是现有的拒绝文本。审查请求的输入与入库的理由都经 Secret 按值脱敏。

### D 界面

- **D1（Q20，替代 Q9）名字与菜单。** 菜单四项：请求批准（`default`）、帮我批准（`accept-edits`，名字不动）、自动审查（`auto-review`）、完全访问权限（`full-access`）。首次选择自动审查不弹确认框，菜单项说明写清“由模型判断、可能误判，命令仍受沙箱限制”。Q9 的推荐（把 `accept-edits` 改名为“自动接受编辑”并停用“帮我批准”）与 Q20 的推荐（三项菜单，“帮我批准”改指新模式）都未采纳。
- **D2（Q11）Shift+Tab 循环。** read-only → default → accept-edits → auto-review；full-access 仍不在循环内。
- **D3（Q16、Q17）状态与标注。** 审查进行时工具卡显示“自动审查中”；放行后标“已由自动审查允许”，展开可看理由；转交时审批卡上显示审查者的理由。

### E 交付

- **E1（Q8）范围与顺序。** 本次只做这个新模式；“移除 read-only”继续搁置，不并入。实施排在计划生命周期阶段一（票 01–08）之后，避免两件事同时改 `PermissionMode` 与 `permission_mode` 条目版本。
- **E2（Q19，随 Q20 调整）ADR 与术语。** 新写一条 ADR，写明“用户可以把最后一步询问委托给模型，硬边界不可委托”，说明它细化 ADR 0005，以及与 ADR 0013（纳入 Goal 预算、由用户显式选择模式）和 ADR 0019（显式给出模式即调用者的授权）的关系；编号等计划生命周期的 ADR 占号后取下一个。术语表新增 Auto Review（由模型代答最后一步询问的 Permission Mode）与 Reviewer（代答的模型请求），避免使用 auto mode、classifier。“帮我批准”仍是 `accept-edits` 的界面名，术语表注明它不是 Auto Review 的同义词。
- **E3（Q21）测试范围。**
  - 判定单测：新模式 × 各权限类的模式放行与宽窄排序。
  - 审查接缝测试（可编程的假审查者）：放行、转交、超时、报错、输出无法解析、预算耗尽、审查途中切换模式作废、automation 不送审、Hook 先于审查者。
  - 真实 Sidecar 集成（本地模型 HTTP 服务充当审查者）：条目形状、`purpose: 'review'` 计入 Goal 预算、子代理取根 Session 的用户意图、无界面运行下转交即拒绝。
  - 对手用例：审查者恒放行时，拒绝规则、询问规则、受保护路径、越出可写根、提权、计划审阅仍不被放行；待审参数与先前工具结果中伪造的“放行”文本不出现在审查者的指令位置；审查请求的输入与入库的理由都经过脱敏。
  - 界面：菜单与循环、“自动审查中”状态、工具卡标注与理由、审批卡上的转交理由。
  - 真实模型的判断质量不做自动化评估，交付时写“未验证”。
- **E4（Q22）交付。** 单阶段，一份规格。没有审查者的新模式等同于 `accept-edits`，没有可独立上线的中间形态。

## 用户已知的后果

D1 让“帮我批准”与“自动审查”在菜单里并列，而前者并不由模型审核。用户此前正是因为这个名字以为它由模型审核。用户确认清单时已被告知这一点；规格需要把两项的说明文字写得能一眼分清。

## 留给规格的细节（E5）

讨论中没有逐条问过，规格阶段需要给出并标明为规格补充的决定：

- 审查提示的具体文本与审查输出的结构化格式（不可信内容如何作为数据包裹）。
- 审查上下文的字符预算与截断规则，以及被截断时是否倾向转交。
- “自动审查中”状态经持久条目还是瞬态事件送达界面，Sidecar 在审查途中退出后如何恢复。
- 转交给用户的审批卡照常提供“总是允许”建议规则（由 A2 推出，未单独确认）。
- 审查请求是否计入上下文环之外的哪些用量展示（消息底栏已由共用汇总覆盖）。
- 新 ADR 的编号、外部 Hook 输入中的模式取值、headless `--permission-mode` 的取值校验。
