# 01: 注入的候选顺序：用户手写的在前

**What to build:** 用户亲手写的记忆最后才会被挤出正文。Memory 段在每一级（项目级、用户级）内先放来源为用户的条目，再放来源为 Agent 的条目，各自按更新时间倒序；用户编辑过的 Agent 条目来源已是用户，按用户来源参与排序。预算与两级分配规则不变，只有每一级内的候选顺序变了。这个顺序只用于注入：`memory_list` 不带参数时的输出、记忆接口的列表与设置页的列表仍按更新时间倒序。

**规格场景:** [spec](../spec.md) 的 AC-07、AC-08，以及 AC-01 中“每一级内用户来源在前”的部分；实现决定“三层与候选顺序”“正文层”；用户故事 4、5。

**文档影响:** [Memory](../../../docs/subsystems/memory.md) 注入一节的排列与验证一节。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] AC-07：一条很早的用户来源条目与合计超过预算的较新的 Agent 来源条目并存时，用户来源的条目在段内，被挤出的是 Agent 来源中较旧的。
- [ ] AC-08：一条 Agent 来源的条目经接口编辑后，在请求的 Memory 段中排在未编辑的 Agent 条目之前。
- [ ] 条目没超预算时，段内每一级为用户来源在前、Agent 来源在后，各自按更新时间倒序；项目级仍在用户级之前。
- [ ] 两级预算的分配、每一级遇到放不下的条目即停止、未放入条数的注明与现状一致。
- [ ] `memory_list` 不带参数的输出、`/api/memories` 的列表与设置页的列表次序不变。
- [ ] 现有按更新时间断言段内排列的单元与集成用例按新顺序改写，不保留旧行为的断言；一条真实 Sidecar（faux 脚本）用例确认请求中的实际排列。
- [ ] 按[测试约定](../../../docs/tech-stack/testing.md#测试执行与结果报告)运行最小相关集与类型检查；实际执行的检查和文档影响记入 Comments。
