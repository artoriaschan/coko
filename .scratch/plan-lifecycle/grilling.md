# 计划从权限模式剥离并延伸到结果反馈：设计树与采纳记录

2026-11-20。本会话先核对了 Plan Mode 的现状（[当前行为](../../docs/subsystems/plan-mode.md)、[ADR 0005](../../docs/adr/0005-permission-mode-and-sandbox.md)），用户提出“计划不应该属于权限模式”，随后调用 `/grill-me` 讨论调整方案。四轮共 24 个问题，用户都答复“全部采用推荐”，并在最后确认了完整清单。本文记录设计树与已采纳的决定；尚无规格、设计与实施票，未改代码，术语表与 ADR 也未改。

## 已核对的事实

来源：一次只读的代码调查（未运行测试），其中“判定分支、沙箱档位、子会话注入、写入工具不经沙箱、审阅时输入区隐藏”五处由主会话对照代码复核。

- **没有独立的“规划中”标志。** 是否在规划（`PlanReview.active()`）、是否注入 `<plan_mode>` 与注册 `exit_plan_mode`、“本次规划”的起点（`nextPlanRef`），都从“当前权限模式是否为 `plan`”推出。
- **判定与沙箱。** `plan` 与 `read-only`、`default` 走同一个放行分支，只放行 Workspace 内读取；沙箱档位为 read-only，可写根为空。
- **写入在规划期间是询问，不是拒绝。** 可写根为空，写入落到“越出可写根”一步，只能允许一次；用户批准后 `write` / `edit` 直接落盘，只读沙箱只约束 bash。
- **依赖面。** 把 `plan` 当权限模式用的非测试代码有七十多处，分布在 `packages/protocol`、`packages/agent`、`apps/server`、`apps/desktop`、`packages/i18n`；涉及的测试文件约 33 个。改动主体是 `apps/server/src/application/session-permissions.ts`。
- **审阅期间够不着模式菜单。** 审批卡接管时输入区整块隐藏，模式菜单与 Shift+Tab 不可用；服务端此时仍接受切换模式，计划请求不重新判定。
- **子代理。** 父会话在 plan 时子会话的有效模式恒为 read-only；子会话会被注入要求调用 `exit_plan_mode` 的 `<plan_mode>`，而该工具对子会话固定排除。定义文件不允许 `plan` 取值。带 worktree 隔离的派发在 plan 与 read-only 下直接拒绝。
- **条目版本。** 条目在读取时于内存中逐版升级，不改写数据库行；`permission_mode` 已有 v1 到 v2 的先例（恒等迁移）。
- **其他入口。** headless 接受 `--permission-mode plan`，无人回答时计划被自动拒绝。首次发送可带 `plan`，此时没有 prior。分叉与交接复制 `permission_mode` 条目，不复制 `plan` 条目。Shift+Tab 从 plan 落到 read-only。外部 Hook 的输入会收到 `plan`。
- **批准之后。** 只提交 approved 的 `plan` 条目、恢复模式、把计划写进工具结果；此外只有压缩后重新注入 `<approved_plan>`。没有“执行中的计划”这类状态，与 Todo 没有任何关联，与 Goal 的唯一关联是 Goal 轮次中审阅时进入等待。
- **相邻机制。** [Todo List](../../docs/subsystems/todo.md) 已提供可见的步骤清单；[Goal](../../docs/subsystems/goal.md) 已提供成功条件、逐条证据、跨多轮自动推进与预算。
- **ADR 0005 的来历。** `plan` 作为模式取值是沿用 claude-code 的形状以一句话加入的，该 ADR 注明按常设指示采纳、未经用户逐条确认。

## 讨论中已定

- **B1 计划不属于权限模式。** 权限模式回答“哪些动作要先问”，计划回答“处在流程的哪个阶段”，两者正交。合在一个字段里的代价：需要 `prior` 记住被顶掉的模式、批准时要校验“不能宽于 prior”、模式菜单在 plan 时三项都不勾选、类型拆成四档与五档两套、“不改文件”的约束是借来的。
- **确认前硬性禁止修改 Workspace 文件，由计划流程自己施加。**

## 第一轮（用户：全部同意，按推荐来）

- **A1（Q1）范围：** 本次只做计划相关调整。移除 `read-only` 模式、“帮我批准”改成大模型审核各自另立；剥离后计划不再借用 `read-only` 的判定，三者互不依赖。
- **C1（Q2）计划的终点：** 计划贯穿到结果反馈，批准后进入“执行中”，直到对照计划汇报完才结束。
- **B2（Q3）规划期间的其余权限：** 读取、bash、MCP 是否询问一律按会话当前的权限模式走。
- **B3（Q4）命令沙箱：** 规划期间命令在只读沙箱里运行，由计划状态施加。否决“沿用权限模式对应的沙箱”（硬性禁止只剩提示词）；“Workspace 只读、临时目录可写”需要新档位，规划时跑测试受阻成为常态再考虑。
- **B4（Q5）写入工具：** 规划期间 `write`、`edit` 这类文件写入工具一律直接返回拒绝：不弹审批、不分路径，允许规则与 Hook 也放行不了。
- **B5（Q6）批准时切换权限：** 批准不再触碰权限模式，去掉 `mode` 参数与“批准并允许编辑”。
- **B7（Q7）进入方式：** 只由用户发起（`/plan` 与协议接口），不新增模型可调用的进入工具。

## 第二轮（用户：全部采用推荐）

- **C2（Q8）任务拆解：** 提示词要求批准后先用 `todo_write` 把计划拆成待办再动手，宿主不设硬门禁。
- **C3（Q9）如何结束：** 新增工具（暂名 `complete_plan`），模型提交 Markdown 完成报告，计划变为已完成；提示词要求逐项对照计划写明做了什么、怎么验证、哪些没做或偏离。宿主不校验内容，不自动跑测试。否决“Run 正常结束即完成”（中途提问会被算成完成）与“批准时自动建 Goal”（每个计划都触发自动续轮与预算）。
- **C4（Q10）完成是否确认：** 不走审批，提交即结束；报告显示在时间线计划卡与右栏 Plan 页。
- **C5（Q11）执行跨多个 Run：** 计划保持执行中，之后的 Run 继续提醒模型有未完成的计划；宿主不自动发起下一轮。
- **C6（Q12）执行中放弃或重新规划：** `/plan off` 或 Plan chip 的 × 为放弃，标记已放弃，不撤销已做的改动。执行中再 `/plan` 先把当前计划标为已放弃，再进入新一轮规划，新计划用新编号。否决“再 `/plan` 等于修订当前计划”与“执行中拒绝 `/plan`”。

## 第三轮（用户：全部采用推荐）

- **B6（Q13）审阅时切换权限：** 审阅卡标出将以哪个权限执行，并放入现有的模式菜单，批准前可改。
- **D1（Q14）子代理：** 规划期间派发的子代理同样禁写、命令在只读沙箱；权限模式不再被压成只读，照常按父会话模式与定义上限取较窄者。带 worktree 隔离的子代理规划期间仍拒绝。子会话只收到“正在规划、不可改动”的说明，不再收到提交计划的指引。
- **D2（Q15）历史会话：** 旧的 `plan` 权限记录读取时按进入前的权限处理，没有记录的按 default，不改写数据库。升级时正停在规划中的旧会话视为已退出规划，已提交的计划仍可查看。
- **D3（Q16）回退：** 计划阶段跟随对话回退：回退到批准之前回到规划中，回退到 `/plan` 之前不在规划中。权限模式现有的回退口径本次不改。
- **D4（Q17）分叉与交接：** 规划中的会话分叉或交接后，新会话也在规划中；计划记录不复制，执行中的计划不带过去。
- **D5（Q18）headless：** 去掉 `--permission-mode plan`，不提供替代参数。
- **D6（Q19）其余连带变化：** Shift+Tab 只切权限，不再退出规划；外部 Hook 收到真实权限模式，不另加“规划中”字段；规划期间向进入规划前启动的可写终端发送输入仍然拒绝；定时任务在规划中的会话上照常带规划提示运行；新对话首次发送不能再带 `plan` 权限，`/plan …` 照常可用。

## 第四轮（用户：全部采用推荐）

- **E1（Q20）术语：** Plan Mode（计划模式）是会话的规划阶段，从 `/plan` 到计划被批准为止，期间不改动 Workspace，不再是权限模式。Plan（计划）是贯穿生命周期的方案，状态为待审阅、已拒绝、执行中、已完成、已放弃。`/plan`、`exit_plan_mode`、`<plan_mode>` 的名字保留，新工具叫 `complete_plan`。
- **E2（Q21）交付拆分：** 分两步，各自独立验收。第一步剥离（B、D 两支与 B6），存储按完整生命周期设计；第二步生命周期（C 一支与 E3）。
- **E3（Q22）Plan chip：** 规划中显示“计划”，执行中显示“执行中”，样式不变；× 即放弃，不弹二次确认；完成或放弃后 chip 消失。
- **D7（Q23）其余推论：** 一个会话至多一份活动计划（规划中或执行中）。计划完成或放弃后不再向后续 Run 重新注入已批准的计划正文。`complete_plan` 只在有执行中计划时提供，任何权限模式下都不询问，子代理不能调用。记忆写入、Todo、Goal 工具规划期间照常可用。无反馈拒绝、停止时取消审阅、Run 进行中拒绝 `/plan`、Goal 轮次中审阅时进入等待保持现状。
- **E4（Q24）ADR：** 新写一份 ADR 记录“计划是独立的会话状态，不是权限模式；规划期约束由计划流程施加”，并在 ADR 0005 上标注其中“plan 作为模式取值”的部分被它替代。

## 另行记录的缺口

本设计不修，需另开问题：

- 回退不还原权限模式：服务端回放与渲染端用原始条目，分叉与交接用有效条目。回退跨过一次模式切换后，源会话仍是切换后的模式，从它分叉或交接出的会话得到回退前的模式。未找到覆盖这一组合的测试。
- `docs/subsystems/headless.md` 没有提到 `--permission-mode plan`；headless 下计划必然被自动拒绝是从代码推出的，未见测试。
- 首次发送带 `plan` 时没有 prior，退出后回到 default 而不是默认模式设置；当前行为文档只描述了带 prior 的两条进入路径。
- 审阅等待期间经协议切换模式后批准，会落到当前模式而不是 prior；未见测试，文档未说明。
- i18n 的 `plan.modeDescription`、`plan.exitHint` 没有引用。

D5、D6 落地后，上面第二至四项的现象随之消失；第一项与第五项与本设计无关。

## 结论与下一步

设计树已走完，只剩 E5（验收与测试接缝）留到规格阶段。术语表与 ADR 尚未改动：术语表的新定义会与当前行为文档冲突，随第一步交付一起改；ADR 在设计阶段按 E4 写。

规格需覆盖：规划期间各类调用在各权限模式下的判定与沙箱（B2–B4）、审阅卡换权限（B6）、子代理继承（D1）、历史条目的读取兼容（D2）、回退与分叉后的计划阶段（D3、D4）、执行中的提醒与 `complete_plan`（C3–C5）、放弃与重新规划（C6）。
