# M5 复盘

2026-10-31，lead。依据：[lead 记录](lead-notes.md)、两份评审及其"处理结果"、各票 Comments。标"已采纳"的是 lead 在授权范围内已执行的调整，其余为建议。

## 按严重度

1. **评审仍发现授权与恢复的缺口（自动检查）。** 子代理通知在 Goal Round 中让模型获得 user 权限；后台子代理在重启后被描述为"没有副作用，可以重试"；worktree 会话的项目规则、恢复探测与回退边界仍按主 checkout。M4 复盘采纳的"对手用例"规则覆盖了 Hook 与预算，但没有覆盖"新的宿主输入种类"——每加一种宿主注入的消息（job、agent、schedule、hook-context），授权与时间线判断都要同步。已采纳：宿主输入标签收为 `@coko/agent/entries` 一处常量。建议：M6 的票凡是新增宿主注入的消息种类，验收固定包含 runAuthority、Goal 的用户输入判断与时间线三处。
2. **跨控制通道的验收只看一侧（信息获取）。** 票 05 的桌面通知从未显示：单元测试直接调用 main 的处理函数，集成测试只看 Sidecar 发出的消息，lead 合入时也只看了 Sidecar 日志；由票 09 的 E2E 发现。已采纳：控制通道的 switch 与进度种类加穷尽检查（票 11）；子代理通知与通知点击打开会话各有跨通道用例。建议：跨进程的功能，验收至少一条在接收侧观察结果的用例。
3. **并行全量互相重叠，测试大面积超时（自动检查）。** M4 的"开始前等其他 vitest 结束"只在开始时检查，四个实施者与 lead 的全量仍重叠，负载 20–40。已采纳：`/tmp/coko-full-test.lock` 全量测试锁与运行期间的重叠采样；lead 的复核只在锁内、且报告重叠数。另有一处 lead 失误：用 `String.replace` 把锁脚本写进 brief 时 `$$` 变成了 `$`，由实施者发现。
4. **本套件自身负载下的超时，先逐个修补（工具经济）。** 锁之后 main 仍连续三次各有 1 例超时（overlap-max=0）：lead 先给单个文件加预算，下一个文件失败后才改为 Browser Mode 项目级 testTimeout，并把包入口的动态导入移到模块顶层。与 M4 同一教训：先确认失败签名是否同类，同类按配置处理。
5. **真实缺陷藏在"负载超时"里（信息获取）。** sidecar-handoff 的停止用例看似负载超时，读代码后是真实缺陷：run_start 之后、第一次请求之前到达的停止没有可停止的流，请求照常发出。worktrees.test 则确是真实 git 的预算问题。区分两者靠读失败的实际值与代码，不靠重跑。
6. **并行票之间的接口在实施中协商（工具经济）。** 票 11、12 的约定改了两次（交接失败改为新 kind；SCHEDULED_TASK_TAG 带 <），票 12 按旧约定完成，推送用例以 skipIf 等待一个不会发生的协议变化；最后由票 11 补做对齐。建议：可并行的修复票，接口（条目形状、共享常量）在开票时由 lead 定死，写进两张票。
7. **合并冲突集中在 layers.ts 与票 Comments。** 票 03/05、07/10、09/标题栏修复各冲突一次，都保留两侧解决，typecheck 与全量通过。layers.ts 是所有服务的装配点，M6 若继续并行加服务，建议票 02 式的预构建先放好占位。
8. **lead 收到报告后先回复"OK"（工具经济）。** M5 几乎每张票的 MERGE-READY、BLOCKED 与进度提示后都发生，包括 main 变红与合并冲突进行中；一次因此在 typecheck=2 时没有发现失败。M1–M5 一直没有改掉。
9. **真实模型仍未验证。** 本机无密钥。
