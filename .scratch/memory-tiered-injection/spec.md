# 记忆分层注入规格

Status: ready-for-agent

## 来源、确认与实施状态

本规格按 `to-spec` 汇总 2026-11-19 本会话经 `grill-me` 四轮确认的需求。用户在每一轮都回复采纳 Agent 给出的推荐，并在最终总结后回复“确认”。访谈中用户提出过“能否采用合并更新，还是分层设计”，结论是两者都做：分层解决容量，合并只在写入时由模型自己完成。

**实施状态（2026-11-19）。** 01—08 号票已在本地实施并完成联合验收，见[联合证据](evidence/acceptance.md)。AC-01 至 AC-30 有自动化测试证据，跨票联合场景有真实 Sidecar 用例；AC-31、AC-32 的 faux 模式通过，真实模式因本机没有评测用的 Provider 配置与凭据记为 `skipped: no-credentials`，即真实模型是否会按 id 读取摘要层条目、检索落空后是否换说法再查未验证。相近判定（三字符片段，阈值 0.35）对中文的区分度不足：换说法的同义句找不到、句式相同的不同事实会被列出，新建时的相近条目与检索的近似匹配因此只是粗筛，见证据中的说明，未解决。本规格以原批准需求作为 delivered 交付基线；代码在集成分支 `feat/memory-tiered-injection` 上，未合入 main、未推送、未发布。

**实施中补充或调整的细节（未经用户逐条确认）。** 摘要行的标签名为 `<summary>`（与正文层的 `<entry>` 区分），摘要层说明与写入引导新句子的英文措辞由 03 号票确定；`memory_list` 的 `ids: []` 为参数错误（至少 1 个）；相近判定的比例取“给定文本的片段出现在条目正文中的占比”，阈值 0.35 由 04 号票的 29 对样例确定；评测预置记忆只支持用户级（评测的 Workspace 不属于项目），faux 脚本以 `{{memory:N}}` 引用预置条目的 id。

下面几项没有单独成题，列在最终总结的默认项中随用户确认一并生效：用户手写优先只改注入的顺序；相近比对只针对本次 Run 可见的条目；按 id 读取只限可见的条目；设置页的汇总由服务端按当前会话或草稿的项目归属计算；不新增 ADR。验收场景中关于摘要何时带省略号、`ids` 与 `query` 同时给出、未找到的 id 如何呈现等细节，是写规格时为了让场景可判定而补的，未经用户逐条确认，实施前如有异议以用户意见为准。

与现有决定和规格的关系：

- [记忆归属、写入与注入规格](../memory-scope-and-writes/spec.md)已交付，本规格在其之上修改注入、`memory_list` 与 `memory_write` 的结果，不改归属、权限与工具的注册条件。该规格把“中文短词检索的改进”“在界面上提示超出预算未注入的条目”列为范围外；本规格纳入其中的一部分：模型检索的近似匹配，以及设置页按组的汇总（不到每条的标记）。
- [ADR 0027](../../docs/adr/0027-memory-follows-project-writes-without-approval.md) 的项目归属、不经审批与替代审批的限制不变；摘要行同样带来源标注，用户来源的条目仍不可被模型改动。
- [ADR 0024](../../docs/adr/0024-session-state-as-state-updates.md) 的“Memory 属于 system 中的定义、每个 Run 重新读取”不变。
- [ADR 0004](../../docs/adr/0004-model-credentials-safe-storage.md) 之下记忆正文在保存前脱敏的做法不变：摘要取自已脱敏的正文。
- 不新增 ADR：层数、预算与摘要长度是可调的常量与格式。

## Problem Statement

记忆的条目多起来之后，用户会遇到三个问题。

第一，超出预算的记忆悄悄失效。Memory 段的条目正文合计上限是 12 000 字符，超出的条目本次 Run 完全不出现，模型只看到一句“还有 N 条”，要靠它自己想到去检索。界面上没有任何提示，表现只是“Agent 好像忘了”，用户无从判断是不是预算的原因。

第二，用户亲手写的偏好会被 Agent 新记的内容挤掉。每一级内只按更新时间排序，Agent 最近记下的一批条目会把用户很早手写的、更确定的要求排到预算之外。

第三，条目只增不减，检索又找不到。模型新记一条时没有任何机制告诉它已经有相近的条目，重复的条目越积越多；条目到几百条时大部分只能靠检索，而检索要求每个词都出现，模型换一种说法就查不到。

## Solution

超出正文预算的条目不再从 Memory 段消失，而是降为一行摘要：带 id、作用域、来源和正文的第一行。模型看到摘要后需要全文时，用 `memory_list` 按 id 读取。摘要也放不下的条目才只能靠检索，段末仍注明条数。

每一级内先放用户手写的条目，再放 Agent 记下的，用户写下的要求最后才会被降级。

模型新建一条记忆时，工具结果附上相近的已有条目，由它决定是否替换旧的并删除新的；系统不自动合并或删除任何条目。模型检索时严格匹配为空，就退回按相近程度排序的近似匹配。

设置的 Memory 分区在每组下显示有多少条以全文注入、多少条只注入摘要、多少条未注入，让超预算这件事看得见。

## User Stories

1. 作为记忆较多的用户，我希望超出预算的记忆仍然以一行摘要出现在 Agent 眼前，这样它不会因为预算而完全不知道某条记忆存在。
2. 作为用户，我希望 Agent 看到摘要后能按 id 读出全文，这样被降级的记忆仍然能被完整用上。
3. 作为用户，我希望条目没超预算时一切和现在一样，这样这次改动不影响记忆不多的日常使用。
4. 作为用户，我希望我亲手写的记忆优先以全文注入，这样我明确写下的要求不会被 Agent 新记的内容挤到后面。
5. 作为用户，我希望我修改过的 Agent 记忆也享有同样的优先，这样我的修正和我手写的内容待遇一致。
6. 作为项目里工作的用户，我希望项目的记忆摘要不会被大量个人偏好的摘要挤掉，这样摘要这一层也保有当前项目的事实。
7. 作为没有项目的用户，我希望用户级记忆能用满摘要的全部额度，这样分两级不会让我可用的额度变少。
8. 作为用户，我希望摘要是每条记忆自己的第一行，这样我不用为已有的记忆补写任何东西。
9. 作为用户，我希望 Agent 写记忆时把第一行写成能单独看懂的一句话，这样它被降为摘要时仍然有用。
10. 作为用户，我希望摘要一眼能看出是否被截断，这样 Agent 知道什么时候需要去读全文、什么时候摘要已经是全部。
11. 作为用户，我希望摘要行同样标明是 Agent 记的还是我写的，这样被降级的条目不会失去可信度的区分。
12. 作为用户，我希望记忆正文里伪造的标签或来源在摘要里同样不起作用，这样分层不会带来新的注入途径。
13. 作为用户，我希望摘要也放不下时仍然被告知还有多少条没出现，这样 Agent 知道需要去检索。
14. 作为用户，我希望 Agent 新记一条时被告知已经有相近的条目，这样它可以更新旧的而不是再添一条重复的。
15. 作为用户，我希望这个提示不挡住写入，这样判断不准时不会让我要求记住的内容记不下来。
16. 作为用户，我希望相近的条目是我手写的时候，Agent 不去改它而是告诉我，这样我写的内容仍然以我为准。
17. 作为用户，我希望系统不会在我不知情时合并或删除我的记忆，这样记忆的每一次变化都能在对话或设置里找到来由。
18. 作为用户，我希望 Agent 换一种说法检索时仍能找到相近的记忆，这样条目很多时检索不会因为措辞不同而落空。
19. 作为用户，我希望近似匹配的结果被明确标出，这样 Agent 不会把相近的条目当成完全对应的答案。
20. 作为用户，我希望我自己在设置里搜索时仍然是精确匹配，这样我输入什么就找什么。
21. 作为用户，我希望在设置里看到每组有多少条以全文注入、多少条只有摘要、多少条没有注入，这样我能发现记忆已经超出预算。
22. 作为用户，我希望这个数字和 Agent 下一次实际看到的一致，这样我可以据此决定精简哪些记忆。
23. 作为在脚本或 CI 中使用 Coko 的用户，我希望无界面运行同样能看到摘要并按 id 读取全文，这样只读的运行不会比交互的运行少看到记忆。
24. 作为用户，我希望子代理同样能看到摘要并读取全文，这样委派出去的任务了解的事实与主对话一致。
25. 作为运行环境不支持全文索引的用户，我希望分层注入和按 id 读取照常可用，只是没有相近条目提示和近似匹配，这样降级时核心功能不受影响。
26. 作为用户，我希望关闭记忆开关后这些都不出现，这样开关的含义不变。
27. 作为开发者，我希望有评测用例检查“答案只在摘要里的记忆被读出并用上”和“答案只能靠检索找到”，这样分层与检索是否有效可以在真实模型上衡量。

## Implementation Decisions

### 三层与候选顺序

- Memory 段的条目分三层：**正文层**注入完整条目块（现状），**摘要层**每条注入一行，**检索层**不注入、只在段末计数。
- 每一级（项目级、用户级）内的候选顺序改为：先是来源为用户的条目，再是来源为 Agent 的条目，各自按更新时间倒序。正文层与摘要层共用这一个顺序：正文层从队首取，摘要层从正文层没放入的第一条接着取。
- 这个顺序只用于注入。`memory_list` 不带参数时的输出、`/api/memories` 的列表与设置页的列表仍按更新时间倒序。
- 段内的排列为：正文层的项目级、正文层的用户级、摘要层的说明、摘要层的项目级、摘要层的用户级、未放入的条数。

### 正文层

- 预算与分配规则不变：条目块合计上限 12 000 字符，项目级先放至多 6 000，用户级至多为上限减去项目级已用，用户级全部放入仍有余量时接着放尚未放入的项目级；每一级遇到放不下的条目即停止。
- 与现状唯一的差别是每一级内的候选顺序（见上）。

### 摘要层

- 只在正文层有条目没放入时出现。出现时先有一句英文静态说明：以下条目只显示第一行，需要全文时用 `memory_list` 的 `ids` 读取。这句说明不计入预算，没有摘要行时不出现。
- 每条摘要一行，带 id、作用域、来源，以及正文的第一个非空行截到 60 字符（与正文上限相同，按 UTF-16 码元计，不在代理对中间截断）。第一行被截断或正文还有后续内容时以省略号结尾；正文只有一行且不超过 60 字符时完整显示，不带省略号。
- 摘要取自已保存（已脱敏）的正文。其中的结束标签按正文相同的方式转义；伪造的来源标注或开始标签留在该行内，不改变段的结构与其他条目的来源。
- 摘要层的预算是独立的 6 000 字符（每行含标签与一个换行），不占用正文层的 12 000。分配规则与正文层相同：项目级先放至多 3 000，用户级至多为 6 000 减去项目级已用，用户级全部放入仍有余量时接着放尚未放入的项目级；每一级遇到放不下的即停止。没有项目级候选时用户级可用满 6 000。
- 摘要层也没放入的条目属于检索层。段末注明其总条数并提示用 `memory_list` 的 `query` 检索，文字与现状相同，只是条数为总数减去正文层与摘要层的条数。

### 写入引导

- 写入引导增加一句：把正文的第一行写成能单独看懂的一句话，因为条目多时只显示第一行。其余句子不变。
- 声明、写入引导与摘要层说明都是英文静态文本，同一组条件（有无写入工具、有无项目、有无摘要行）下逐字不变，不计入任何一层的预算。

### 按 id 读取

- `memory_list` 增加可选参数 `ids`：一组条目 id，至多 20 个。给出时返回这些条目的完整条目块，次序与给出的次序相同。
- 只能读取本次 Run 可见的条目（用户级与本 Run 的项目记忆 Workspace）。不存在或不可见的 id 不使整次调用失败：结果在条目块之后列出没有找到的 id。
- `ids` 与 `query` 同时给出时作为工具错误返回，提示二者只能用其一。`ids` 超过 20 个在参数校验阶段失败。
- 工具描述说明摘要层的条目用 `ids` 读取全文。`memory_list` 的权限类与注册条件不变，子 Session 与 Headless Run 同样可用。

### 新建时返回相近条目

- `memory_write` 不带 `id`（新建）时照常保存，然后在本次 Run 可见的其他条目中查找与新正文相近的条目，至多 3 条。有结果时工具结果在原有文字之后列出每条的 id、作用域、来源与摘要，并提示：如果与其中某条重复，把内容合并进那条（按 id 替换）并删除刚才新建的这条。
- 相近的条目来源为用户时，结果注明该条目由用户维护、不能改动；模型应在回复中告知用户，是否保留新建的条目由它判断。
- 带 `id`（替换）时不查找。没有相近条目时结果与现状相同。工具结果的 details 不变。
- 系统不自动合并、替换或删除任何条目。

### 相近程度的判定

- 相近程度由存储层判定并排序，工具不重排：把给定文本切成三字符片段，按与条目正文重合的片段排序，重合程度低于阈值的不算相近。阈值的初始值在实施时用一组中文、英文与中英混合的样例确定，写入当前行为文档。
- 文本不足三个字符时没有片段，没有相近结果。
- 这项能力依赖 FTS5 的 trigram 索引。运行时没有 FTS5（包括测试用的强制降级）时没有相近结果，写入与检索的其余行为不受影响。
- 工具端口相应增加“按文本查找相近条目”的能力，可见范围与列表、检索相同。

### 检索的近似匹配

- `memory_list` 带 `query` 时先做现有的严格匹配（每个词都出现）。有结果时行为不变。
- 严格匹配为空时，用查询文本查找相近的条目，至多 20 条。有结果时，结果的第一行注明没有完全匹配、以下是相近的条目，随后是条目块；仍然没有时返回现有的“没有匹配”文字。
- `scope` 参数对近似匹配同样生效。
- `/api/memories` 的 `query` 不变，仍只做严格匹配；设置页的搜索框因此保持精确。

### 设置页的汇总

- `/api/memories` 的列表响应增加注入汇总：用户级一组、给出 `workspaceId` 时另有该 Workspace 一组，每组三个数——以全文注入的条数、只注入摘要的条数、未注入的条数。计算与 Memory 段使用同一套分层函数，口径是“此刻以这个可见范围开始一个 Run 会怎样分层”。
- 带 `query` 或 `scope` 时不返回汇总。
- 设置的 Memory 分区在每组标题下显示一行汇总；该组没有条目时不显示，搜索状态下不显示。文案经 zh / en 字典提供。不给每条单独打标记。
- 汇总跟随分区现有的项目归属：项目对话与选了项目的草稿显示两组的汇总，独立对话只有用户级。

### 不变的部分

- 条目的存储、作用域、来源、正文上限与脱敏不变，不新增 schema 版本，不迁移数据。
- 记忆工具的注册条件、权限类与记忆开关不变。开关关闭时不注入、不注册工具；汇总仍可在设置页看到（分区与接口照常可用）。
- 工具卡与工具详情不变。相近条目只出现在 `memory_write` 的结果文字中。

## 验收场景

每条按“前提 → 操作 → 可观察结果”书写；“请求”指实际发给模型的请求。

| 编号 | 场景 |
| --- | --- |
| AC-01 | 可见条目的条目块合计不超过正文层预算 → 发送 → Memory 段没有摘要层说明与摘要行，除每一级内用户来源在前外与现状相同 |
| AC-02 | 不属于项目的 Session，用户级条目合计超过 12 000 字符 → 发送 → 正文层之后出现摘要层说明与摘要行；每行带 id、作用域、来源与不超过 60 字符的第一行；摘要行合计不超过 6 000 字符；正文层仍不超过 12 000 字符 |
| AC-03 | 摘要层中三条条目：正文多行、首行超过 60 字符、单行且不超过 60 字符 → 发送 → 前两条的摘要以省略号结尾，第三条完整显示且没有省略号 |
| AC-04 | 条目多到摘要层也放不下 → 发送 → 段末注明的未放入条数等于可见条目总数减去正文层与摘要层的条数，并提示用 `query` 检索 |
| AC-05 | 项目 Session，项目级与用户级各有许多条目落到摘要层 → 发送 → 摘要层中项目级在前且不超过 3 000 字符，摘要行合计不超过 6 000 字符 |
| AC-06 | 项目 Session，落到摘要层的项目级条目很少、用户级很多 → 发送 → 项目级摘要全部在段内，用户级摘要用到约 6 000 减去项目级已用；反过来（项目级多、用户级少）时用户级摘要全部在段内，余量给项目级 |
| AC-07 | 一条很早的用户来源条目，以及合计超过预算的较新的 Agent 来源条目 → 发送 → 用户来源的条目在正文层，被降到摘要层的是 Agent 来源中较旧的 |
| AC-08 | 一条 Agent 来源的条目，用户经接口编辑后 → 发送 → 它按用户来源参与排序，排在未编辑的 Agent 条目之前 |
| AC-09 | 落在摘要层的条目，正文第一行含伪造的结束标签、开始标签与来源标注 → 发送 → 摘要行内的结束标签被转义，段的结构与其他条目的来源标注不变（对手用例） |
| AC-10 | 落在摘要层的条目，正文在保存时含凭据形态的文本 → 发送 → 摘要行中只有脱敏后的文本 |
| AC-11 | 记忆开启、有写入工具 → 发送 → 写入引导含“第一行写成能单独看懂的一句话”；有无摘要行两种情况下固定文本各自逐字不变，且不计入预算 |
| AC-12 | 摘要层有一条条目 → 模型以 `ids` 调用 `memory_list` → 返回该条目的完整条目块 |
| AC-13 | `ids` 中含一个不存在的 id 和一个属于其他项目的 id，以及一个可见的 id → 调用 → 返回可见的那条，并列出另外两个 id 没有找到 |
| AC-14 | `ids` 给出 21 个 → 参数错误，不执行；`ids` 与 `query` 同时给出 → 工具错误 |
| AC-15 | 子 Session 与 Headless Run，条目超过正文层预算 → 请求 → Memory 段有摘要层，`memory_list` 有 `ids` 参数，按 id 读取返回全文 |
| AC-16 | 已有一条“用户偏好 pnpm 而不是 npm”，模型新建一条内容相近的条目 → 条目已保存；工具结果列出已有那条的 id、作用域、来源与摘要，并提示合并与删除 |
| AC-17 | 没有相近的条目 → 模型新建 → 工具结果与现状相同 |
| AC-18 | 相近的已有条目来源为用户 → 模型新建 → 结果列出该条目并注明由用户维护、不能改动 |
| AC-19 | 模型带 `id` 替换一条条目，库中另有相近的条目 → 结果不列出相近条目 |
| AC-20 | 相近的条目只存在于另一个项目的项目记忆中 → 模型在当前项目新建 → 结果不列出它 |
| AC-21 | 运行时没有 FTS5 → 模型新建一条与已有条目相近的条目 → 保存成功，结果不列出相近条目 |
| AC-22 | 库中有一条条目，模型用措辞不同、严格匹配为空的 `query` 检索 → 结果第一行注明没有完全匹配，随后是该条目 |
| AC-23 | `query` 的严格匹配有结果 → 结果与现状相同，没有近似匹配的说明 |
| AC-24 | `query` 既没有严格匹配也没有相近条目 → 返回现有的“没有匹配”文字 |
| AC-25 | AC-22 的同一个查询经 `/api/memories?query=` 请求 → 返回空列表 |
| AC-26 | 运行时没有 FTS5 → AC-22 的检索 → 返回现有的“没有匹配”文字 |
| AC-27 | 项目的可见条目超过正文层与摘要层预算 → 以项目主要 Workspace 请求 `/api/memories` → 响应含两组的全文、仅摘要、未注入条数，三者之和等于该组条数，且与同一时刻发起的 Run 的请求中各层的条数一致 |
| AC-28 | 同 AC-27，带 `query` 或 `scope` 请求 → 响应没有汇总 |
| AC-29 | 桌面应用，项目对话的设置 → Memory 分区的“用户级”与“项目：<项目名>”两组各有一行汇总；独立对话只有用户级一组的汇总；没有条目的组不显示；输入搜索词后不显示；zh 与 en、明暗主题下文字可读 |
| AC-30 | 记忆开关关闭 → 发送 → 请求中没有 Memory 段与记忆工具 |

| AC-32 | 评测用例“靠检索找到记忆”：预置的条目使答案所在的条目落在检索层 → faux 模式运行 → 模型用与正文措辞不同的 `query` 找到它并写入文件，用例通过；真实模式同 AC-31 |

## Testing Decisions

好的测试只验证外部行为：实际发给模型的请求里有什么、工具结果是什么、接口返回什么、界面显示什么。不测试分层函数如何被调用、相近程度如何计算。

- **主接缝：Sidecar 集成测试。** 复用现有的真实 Sidecar harness 与 faux 脚本，用请求日志断言 Memory 段的各层，用工具结果断言按 id 读取、相近条目与近似匹配，用记忆接口断言汇总。覆盖 AC-02、AC-04 至 AC-10、AC-12 至 AC-28、AC-30。先例是现有的记忆、记忆项目归属与记忆检索的 Sidecar 用例；检索与相近条目的用例沿用“同一组用例在 FTS5 与强制降级下各跑一次”的做法，降级一侧断言不提供。
- **对手用例。** 沿用已确立的做法，为信任边界各加一条：摘要行中的伪造标签与来源（AC-09）、摘要行中的凭据（AC-10，沿用现有脱敏门禁用例的写法）、相近条目的列表中不出现不可见的条目（AC-20）。
- **单元：** Memory 段的组成是纯函数，覆盖候选顺序、两层各自的两级分配与边界（恰好等于上限、单条放不下、没有项目级、余量回流）、摘要的截断与省略号、固定文本逐字不变（AC-01 至 AC-11）。先例是现有的记忆 section 单元测试，其中按更新时间断言排列的用例按新的候选顺序改写。工具的单元测试覆盖 `ids` 的次序、未找到、与 `query` 互斥和上限。
- **存储：** 相近查找在仓库契约测试中覆盖排序、阈值、可见范围与不足三个字符的输入，内存实现与 SQLite 实现各一份；内存实现不必复现相关度，只需满足契约中可断言的部分。
- **桌面：** Browser Mode 测试覆盖 AC-29 的汇总在有无项目、有无条目、搜索状态与两种语言和主题下的显示。不新增 Electron E2E。
- **评测：** 新增两个 Eval Case（AC-31、AC-32）。评测运行器需要两项新能力：在 Run 开始前经记忆接口预置一组条目；faux 脚本能引用预置条目的 id（预置后由运行器替换占位符）。真实模式的结果按“真实模型测试单独报告”的规则处理，缺少凭据时记为未验证，不阻塞交付。
- 不新增接缝；记忆的读取一律经 Sidecar 的工具端口或 HTTP 接口。

## Out of Scope

- 语义检索（embedding）与为上千条条目所做的设计。
- 后台自动合并、自动删除与条目过期。
- 单条正文 2000 字符的上限、按 token 计算预算、条目置顶。
- 给每条条目标记它所在的层，以及在设置页之外的地方提示超预算。
- 设置页搜索框的近似匹配。
- 条目变化对提示缓存的影响。
- 会话结束后自动提取记忆。
- 把存储与协议中的 `workspace` 字面值改名；权限模式与计划流程的调整。

## Further Notes

- **规模的估算基于假设。** 条目 id 是 36 字符的 UUID，条目块的标签约占 95 字符。按平均每条正文 150 字符估算，正文层约放 50 条，摘要层约再放 45 条，其余在检索层。库中目前没有条目，没有真实分布；数字是常量，可以在有数据后调整。
- **相近判定对中文的效果没有验证。** 三字符片段的做法对没有空格的中文是否足够区分相近与不相近，实施前没有数据。它同时支撑新建时的相近条目与检索的近似匹配；如果效果差，这两项的价值会打折，分层注入与按 id 读取不受影响。阈值在实施时确定并记录，实际效果在有真实条目后复核。
- **真实模型未验证。** 模型看到摘要后会不会主动按 id 读取、检索落空后会不会换说法再查，只能由 AC-31、AC-32 的真实模式回答；本机目前没有用于评测的 Provider 凭据。faux 通过只说明链路可用。
- **系统提示变长。** 摘要层出现时系统提示最多再长 6 000 字符加一句说明，每个 Run 都计入；条目没超正文层预算时没有增加。
- **现有排序行为改变。** 每一级内用户来源在前，是对已交付行为的改动：条目没超预算时段内的排列也会不同。相关的单元与集成断言需要改写，不保留旧行为的断言。
- **文档影响。** 实施时需要同步 [Memory](../../docs/subsystems/memory.md) 的注入、检索、工具、协议、界面与验证各节及其 frontmatter 摘要；[文档导航](../../docs/README.md)中 Memory 一行的摘要；[追踪、审计、导出与评测](../../docs/subsystems/tracing.md)的用例格式表与当前用例；[测试约定](../../docs/tech-stack/testing.md)中列举评测判定依据处；承载记忆存储契约说明的包 README 如有对应描述则同步。
