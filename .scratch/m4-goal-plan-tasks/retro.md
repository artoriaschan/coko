# M4 复盘

2026-10-30，lead。按 retro skill 分类；标"已采纳"的是 lead 在授权范围内直接执行的调整，其余为建议。依据：[lead 记录](lead-notes.md)、两份评审及其处理结果、各票 Comments。

## 按严重度

1. **评审仍发现无人值守花费与越权的缺口（自动检查）。** 工具调用预算可被命令输出的文本前缀绕过（A2）、取消进行中可恢复并开出不受预算约束的 Goal Round（A3）、压缩摘要不经预算检查（A4）、PTY 在 Plan Mode 下仍按原档位执行输入（A1）、拆分 `job_input` 可绕过 deny 规则（Spec 3）。各票的验收覆盖了"正常路径被拦下"，没有覆盖"模型或命令主动构造的绕过"。建议：M5 起，凡是预算、权限或沙箱判定的票，验收中固定加一条"对手用例"——由模型或命令输出构造的输入不能改变判定结果。
2. **组合后才出现的失败（信息获取）。** 票 09 合入后自动压缩用例确定性失败：多张票各自增加工具定义，各自全量都绿，合在一起越过测试的固定阈值。只有 lead 在 main 上的合入后复核能发现，保留这一步（已采纳）。
3. **只在全量负载下出现的测试问题（自动检查）。** 一天内修了七个：5 秒 / 30 秒超时（三次）、send 后只读一次 job_start、bash 在 wait 前收到信号以 0 退出、Browser Mode 文件之间的 localStorage 草稿泄漏、命令菜单晚于 Esc 出现、unmount 未 await。已采纳：implementer-brief 加"运行全量前等其他 vitest run 结束"；Browser Mode 共享 afterEach 断言没有 Radix 残留；写 localStorage 的测试自行清理。建议：在测试约定中补一句"按键序列前等待编辑区或菜单的可观察状态"。
4. **诊断时先猜原因（工具经济）。** goal-card 的失败先按"按键晚到"修了两轮，读到断言的实际值后才发现是另一个文件的草稿泄漏。建议：修复只在全量下出现的失败前，先读失败的实际值与最近的写入者，再假设原因。
5. **实施者中断（工具经济）。** 票 02 与评审修复票各有一位实施者中途失败；前者留下 4 个提交可接续，后者一个提交都没有。已采纳：接续时要求"每完成一项就提交"，第二次的接续者按此完成 19 个提交。建议写入 implementer-brief 的通用规则。
6. **实施者写入主仓库检出。** 票 10、11 的实施者把票文件或截图写进了主仓库检出（未提交）。lead 合入前检查 `git status`，保留更完整的票记录、删除截图。已采纳：评审修复票的 prompt 明确"只在 worktree 中写文件"，本次没有再发生。
7. **lead 收到完成报告后先回复"OK"（工具经济）。** M4 中几乎每张票都发生，包括 main 变红时。流程没有因此出错，下一步都执行了合入与复核，但用户看到的是空回复。这是 M1–M4 一直没有改掉的习惯。
8. **真实模型仍未验证。** 本机无密钥。
